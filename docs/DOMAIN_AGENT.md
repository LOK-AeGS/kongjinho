# 도메인 평가 에이전트 설계

KV cache 최적화 기술 두 건(SW: DeepSeek-V2 MLA, HW: ITME CXL-Hybrid)이
**데이터센터** 환경에서 각각 어떤 조건에서 적합하다고 평가받는지 조사하는 에이전트입니다.
우열을 판정하지 않고, 관점에 따라 평가가 어떻게 갈리는지를 근거와 함께 기록합니다.

부모 그래프에서는 `domain` 노드로 주입되며 `domain_findings` 키 하나만 반환합니다.
흐름은 `outputs/agent-architecture/mermaid/06-domain-evaluation.mmd`를 그대로 따릅니다.

## 평가 도메인을 데이터센터로 고정한 이유

KV cache 문제의 본질은 연산 병목이 아니라 메모리 병목입니다. 문맥이 길어질수록 저장해야 할
Key-Value가 선형으로 늘어나 가속기의 HBM 용량을 소진하는데, 이 압박이 실제 비용으로 환산되는
곳이 데이터센터입니다. 온디바이스에서는 단일 사용자가 자기 메모리를 쓰고 끝나지만,
데이터센터에서는 한 요청이 붙잡은 KV cache가 곧바로 다른 사용자 몫의 HBM을 잠식하고
동시 처리 가능한 요청 수를 떨어뜨립니다. 즉 같은 기술이라도 "메모리를 얼마나 아끼는가"가
매출과 직결되는 환경이 데이터센터이므로, 평가 기준이 가장 선명하게 드러납니다.

두 번째 이유는 비교 가능성입니다. 선정한 HW 기술인 ITME는 CXL 기반 disaggregated memory를
전제로 합니다. CXL은 랙 스케일 인터커넥트 규격이라 온디바이스나 엣지 환경에는 존재하지 않고,
따라서 그 환경을 도메인으로 잡으면 HW 진영 기술은 평가 자체가 성립하지 않습니다.
SW 압축과 HW 메모리 확장이 같은 무대에서 경쟁하는 환경은 데이터센터가 사실상 유일합니다.

세 번째는 평가 지표가 정량적으로 존재한다는 점입니다. 데이터센터는 처리량(tokens/s),
동시 처리 요청 수, HBM 점유량, 랙 전력 예산, 토큰당 비용처럼 이미 합의된 지표를 가지고 있어
"좋다/나쁘다"는 주관 판단을 줄이고 조건부 판단으로 환원할 수 있습니다.
두 논문이 내세우는 수치(MLA의 KV cache 93.3% 감소, ITME의 처리량 1.80배 향상)도
모두 이 환경을 전제로 측정된 값이라 실험 조건과 목표 환경의 간극이 상대적으로 작습니다.

다만 이 선택에는 한계가 있습니다. 데이터센터로 고정하면 "온디바이스에서는 MLA가 더 유리하다"
같은 반대 방향 평가를 놓칠 수 있습니다. 이 한계는 `domain_findings`의 `completion.gaps`와
보고서 한계점 장에 명시합니다.

## RAG를 적용한 이유

도메인 평가는 모델이 이미 알고 있는 지식을 꺼내 쓰는 작업이 아니라,
특정 환경의 요구사항과 기술의 실측값을 대조하는 작업입니다. 다음 세 가지 이유로
검색 증강이 필수였습니다.

첫 번째는 시점 문제입니다. 선정한 ITME 논문은 2026년 6월 공개된 자료로, 평가에 사용하는
GPT 계열 모델의 학습 데이터 절단 시점 이후일 가능성이 높습니다. 모델 파라미터에만 의존하면
존재하지 않는 수치를 지어내거나 유사한 다른 CXL 연구와 혼동할 위험이 큽니다.
실제로 이 프로젝트는 "1.80배 처리량 향상"이라는 구체적 수치를 근거로 다뤄야 하므로
원문 대조 없이는 검증이 불가능합니다.

두 번째는 출처 추적 의무입니다. 최종 산출물인 평가 보고서는 REFERENCE 장에 실제로 활용한
자료만 형식에 맞춰 기재해야 하고, 각 주장은 어떤 문서 몇 페이지에서 나왔는지 연결되어야 합니다.
팀의 `state.py`가 `Evidence`에 `url`, `page`, `excerpt`, `accessed_date`를 요구하는 것도
같은 이유입니다. 검색 단계에서 출처 메타데이터를 함께 확보하지 않으면
보고서 단계에서 사후에 복원할 방법이 없습니다.

세 번째는 확증편향 방지입니다. LLM에게 "이 기술이 데이터센터에 적합한가"를 그냥 물으면
논문의 주장을 그대로 반복하는 긍정 편향이 나타납니다. 검색 질문을 생성할 때
기대 효과와 제약·실패 조건을 모두 묻도록 강제하고, 확보한 근거로만 주장을 세우게 하면
"근거를 찾지 못했다"는 판단 보류(`assessment: unknown`)가 가능해집니다.

## 검색 범위와 출처 신뢰도

검색 대상은 팀이 선정한 문서 풀(총 200페이지 이내)입니다. 인덱스 구축 자체는 공유 RAG 준비
단계가 담당하고, 이 에이전트는 완성된 검색 도구를 주입받아 질의만 수행합니다.
`Retriever` 프로토콜(`search(query, k) -> list[SearchHit]`)만 만족하면 어떤 구현이든
교체할 수 있게 했습니다. 인덱스 구현과 에이전트 로직을 같이 묶으면 팀원이 인덱스를 바꿀 때마다
에이전트를 고쳐야 하기 때문입니다.

한때 웹 검색(Tavily)을 함께 쓰는 구성도 검토했지만 제외했습니다. 실제로 붙여 본 결과
Tavily의 `include_domains` 화이트리스트가 지정 도메인 수가 늘어나면 지켜지지 않았고
(13개 지정 시 medium·substack·youtube가 그대로 반환됨), 공신력 있는 근거만 쓰겠다는 기준을
서버 측 필터에 맡길 수 없다는 점이 드러났습니다. 클라이언트에서 재차 거르는 방법도 있지만,
과제가 요구하는 RAG는 선정 문서 풀 기반이고 논문 두 편이 모두 데이터센터 환경을 전제로
측정된 자료이므로 문서 검색만으로 도메인 평가가 성립한다고 판단했습니다.

수집한 근거에는 `source_type`을 부여해 `paper`·`official_web`·`news`·`community` 순으로
신뢰도를 구분합니다. 커뮤니티 수준 출처만으로 뒷받침되는 주장은 `basis`를
`direct_evidence`로 올리지 않고 `inference`로 낮춥니다.

## 임베딩 모델 선정

과제 요구사항에 따라 오픈소스 임베딩만 사용합니다. 후보와 검토 내용은 다음과 같습니다.

| 후보 | 라이선스 | 최대 입력 | 검토 결과 |
|---|---|---|---|
| BAAI/bge-m3 | MIT | 8192 토큰 | **선정** |
| intfloat/multilingual-e5-large | MIT | 512 토큰 | 논문 청크가 자주 잘림 |
| nlpai-lab/KURE-v1 | MIT | 512 토큰 | 한국어 특화, 영어 논문 검색에 불리 |
| sentence-transformers/all-MiniLM-L6-v2 | Apache-2.0 | 256 토큰 | 영어 전용, 한국어 질의 불가 |

BGE-M3를 선정한 결정적 이유는 교차 언어 검색입니다. 이 프로젝트는 평가 질문을 한국어로
생성하는데 검색 대상 논문은 영어입니다. 질의와 문서의 언어가 다른 상황에서 같은 벡터 공간에
정렬되지 않으면 검색이 무너지는데, BGE-M3는 100개 이상 언어를 단일 공간에 학습해 이 문제를
직접 겨냥한 모델입니다. 8192 토큰 입력 한도 역시 논문의 표·수식이 포함된 긴 청크를
자르지 않고 담을 수 있어 유리했습니다.

실제 인덱스 구축은 팀의 공유 RAG 준비 단계가 담당하므로 이 에이전트는 모델을 직접 로드하지
않습니다. 다만 공유 인덱스가 준비되기 전에도 동작을 확인할 수 있도록,
`notebooks/06-domain-agent.ipynb`에 위 모델로 논문 두 편을 색인하는 최소 데모를 넣었습니다.
데모용이며 팀의 공유 검색 도구가 완성되면 그것으로 교체합니다.

## 종합 평가 에이전트로 넘기는 데이터 설계

평가 결과를 긴 산문으로 넘기면 종합 단계에서 내용이 희석됩니다. 여러 관점의 텍스트가
프롬프트에 함께 들어가면 모델이 어느 주장이 어느 근거에 붙어 있었는지 잃어버리고,
결과적으로 "대체로 유망하다" 같은 뭉뚱그린 종합이 나옵니다. 그래서 산문 대신
구조화된 레코드로 넘기며, 다음 세 가지 제약을 코드에서 강제합니다.

주장은 한 건당 한 문장으로 제한합니다(`MAX_STATEMENT_CHARS = 240`). 길어지면 여러 논점이
한 레코드에 섞여 종합 단계에서 분해가 불가능해집니다.

판단은 자유 서술이 아니라 열거형으로 고정합니다. `assessment`는
`suitable`·`conditional`·`unsuitable`·`unknown` 중 하나이고, `basis`는
`direct_evidence`·`inference`·`unknown` 중 하나입니다. 종합 에이전트는 이 값만 보고도
관점 간 상충 지점을 기계적으로 찾을 수 있습니다.

근거 본문은 전달하지 않고 ID로 참조합니다. `Claim.evidence_ids`가 `domain:ev:003` 형태로
가리키고, 실제 원문은 `domain_findings.evidence`에 한 번만 보관합니다. 종합 단계는
필요할 때만 ID로 조회하므로 프롬프트에 같은 인용문이 반복되지 않습니다.

이 참조 구조를 만드는 과정에서 한 번 크게 틀렸던 부분을 남겨 둡니다. 최종 `claim_id`는
검증 단계가 부여하므로 모델이 미리 알 수 없어서, 처음에는 모델에게 주장의 순번(1, 2, 3…)으로
판정을 연결하게 했습니다. 그런데 실행해 보니 모델이 자리를 세다 어긋나 SW 판정이 HW 주장을
가리키는 결과가 나왔습니다. 더 나쁜 점은 참조된 ID 자체는 유효했기 때문에
"존재하는 ID인가"만 보던 검사가 이것을 통과시켰다는 것입니다. 지금은 모델이 주장마다
`claim_key`를 직접 붙이고 판정이 그 키를 되짚게 했고, 여기에 더해 판정의 `technology_id`와
주장의 `technology_ids`가 어긋나면 연결을 끊고 `gaps`에 남기는 검사를 넣었습니다.
ID 유효성 검사만으로는 이런 의미적 오류가 드러나지 않습니다.

## 확증편향 방지 조치

검색 질문 생성 단계에서 기대 효과를 묻는 질문과 제약·실패 조건을 묻는 질문을
짝으로 만들도록 프롬프트에 명시했습니다. 한쪽만 생성되면 검색 결과도 한쪽으로 쏠립니다.

근거가 부족할 때 추정으로 메우지 않고 `assessment: unknown`과 `completion.gaps`로
남기도록 했습니다. 판단 보류를 실패가 아니라 정상 출력으로 취급합니다.

실험 환경과 데이터센터 환경의 차이는 `conditions`에 별도로 기록합니다.
논문의 측정값을 그대로 도메인 적합성 근거로 쓰지 않고, 어떤 전제에서 성립하는 수치인지를
함께 남겨 종합 단계에서 조건이 다른 비교가 이루어지지 않게 합니다.

## 파일 구성

| 경로 | 역할 |
|---|---|
| `agents/domain_agent.py` | 에이전트 서브그래프, `Retriever` 계약, 부모 그래프용 진입 함수 |
| `prompts/domain.py` | 프롬프트 템플릿과 데이터센터 도메인 프로파일 |

| `tests/test_domain_agent.py` | 근거 강등·교차 참조 가드 검증 (LLM 호출 없음) |

## 부모 그래프 연결

```python
from agents.domain_agent import build_domain_agent, make_deps

domain_node = build_domain_agent(make_deps(retriever=팀_공유_검색도구))
app = build_graph(technical=..., market=..., stakeholder=..., domain=domain_node, ...)
```

`domain_node`는 `{"domain_findings": ...}` 한 키만 반환하므로 병렬 분기에서
다른 관점 에이전트와 키가 충돌하지 않습니다.
